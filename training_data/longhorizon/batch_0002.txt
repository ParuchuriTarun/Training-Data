@@@ USER
Heap is flat for 3 days. But now CPU is high because we parse every time. Can we cache smarter?
@@@ ASSISTANT
Yes — cache on disk, not in memory. PDF parsing is CPU-bound, not memory-bound, so a shared, bounded disk cache gives the hit rate without the leak.

```ts
import { createReadStream } from "node:fs";
import { createHash } from "node:crypto";

const CACHE_DIR = "/var/cache/reports";

async function cachedReport(id: string) {
  const digest = createHash("sha256").update(id).digest("hex").slice(0, 32);
  const path = `${CACHE_DIR}/${digest}.json`;
  try {
    return await readJson(path); // hit
  } catch {
    const report = await parseReport(id);
    await writeJsonAtomic(path, report);
    return report;
  }
}
```

@@@ USER
Checkout is overselling inventory under load. Two orders for the last unit both succeed. Our code checks stock then decrements. Inventory is in Postgres. How do I reproduce and fix it?
@@@ ASSISTANT

Reproduction:

1. Seed one product with stock = 1.
2. Fire 50 concurrent orders for that product.
3. Count successful orders. Expect > 1 (the bug).

```ts

  Array.from({ length: 50 }, () => createOrder(productId, 1))
);

```

Fix: make the decrement atomic and conditional on stock. Do it in one SQL statement.

```sql
UPDATE inventory
SET stock = stock - 1
WHERE product_id = $1 AND stock >= 1
RETURNING stock;
```

```ts
async function createOrder(productId: string, qty: number) {
  return db.transaction(async (tx) => {
    const updated = await tx.query(
      `UPDATE inventory SET stock = stock - $2
       WHERE product_id = $1 AND stock >= $2
       RETURNING stock`,
      [productId, qty]
    );
    if (updated.rows.length === 0) {
      throw new Error("insufficient_stock");
    }
    return tx.query(
      `INSERT INTO orders (product_id, quantity) VALUES ($1, $2) RETURNING *`,
      [productId, qty]
    ).then(r => r.rows[0]);
  });
}
```

The database now guarantees stock never goes negative; the `WHERE stock >= qty` is the check, inside the same statement as the write. Re-run the 50-concurrent test. Expect exactly 1 success and 49 `insufficient_stock` errors. What does your current stock check look like — do you read stock in application code first?
@@@ END

@@@ USER
Our code does `SELECT stock`, checks in JS, then `UPDATE stock = stock - qty` in one transaction at READ COMMITTED. Is that safe?
@@@ ASSISTANT
No. At `READ COMMITTED`, two transactions can both `SELECT 1`, both pass the JS check, and both `UPDATE` — each seeing the other's uncommitted write is invisible, so both succeed. You need row locks.

Fix with `SELECT ... FOR UPDATE`:

```ts
async function createOrder(productId: string, qty: number) {
  return db.transaction(async (tx) => {
    const row = await tx.query(
      `SELECT stock FROM inventory WHERE product_id = $1 FOR UPDATE`,
      [productId]
    ).then(r => r.rows[0]);

    if (!row || row.stock < qty) throw new Error("insufficient_stock");

    await tx.query(
      `UPDATE inventory SET stock = stock - $2 WHERE product_id = $1`,
      [productId, qty]
    );
    return tx.query(
      `INSERT INTO orders (product_id, quantity) VALUES ($1, $2) RETURNING *`,
      [productId, qty]
    ).then(r => r.rows[0]);
  });
}
```

`FOR UPDATE` locks the row until commit, so concurrent transactions serialize on that row. The conditional single-statement update is simpler and faster; the `FOR UPDATE` version is better when you need to read the pre-decrement stock or validate multiple fields.

Also add a database invariant as a backstop:

```sql
ALTER TABLE inventory ADD CONSTRAINT inventory_stock_nonnegative CHECK (stock >= 0);
```

Deadlock risk: if a transaction locks multiple inventory rows, lock them in ascending `product_id` order. How many products does a single order contain in your case?
@@@ END

@@@ USER
Orders have up to 5 line items. After the fix we saw deadlocks in logs. How do we avoid them?
@@@ ASSISTANT
Lock inventory rows in a deterministic order: sort the line items by `product_id` before locking. Two transactions that lock in the same order cannot deadlock on that set.

```ts
async function createOrder(items: { productId: string; qty: number }[]) {
  const sorted = [...items].sort((a, b) => a.productId.localeCompare(b.productId));
  return db.transaction(async (tx) => {
    for (const item of sorted) {
      const row = await tx.query(
        `SELECT stock FROM inventory WHERE product_id = $1 FOR UPDATE`,
        [item.productId]
      ).then(r => r.rows[0]);
      if (!row || row.stock < item.qty) throw new Error("insufficient_stock");
      await tx.query(
        `UPDATE inventory SET stock = stock - $2 WHERE product_id = $1`,
        [item.productId, item.qty]
      );
    }
    // insert order + lines...
  });
}
```

Additional defenses:
- Set `lock_timeout = '5s'` so a deadlock becomes a fast error, not a hang.
- Retry the whole transaction on `40P01` (deadlock detected) up to 3 times with jitter. Deadlocks are retryable; validation errors are not.
- Keep transactions short: do not call external APIs inside.
- Add a unique constraint on `(order_id, product_id)` so a retried transaction cannot double-insert lines.
- Monitor deadlock count; a rising count means ordering is not enforced somewhere.

Test: run 200 concurrent multi-item orders with overlapping product sets and assert zero oversells and a low deadlock rate (< 1% with retries). How are you currently handling `40P01` errors — retrying or returning 500?

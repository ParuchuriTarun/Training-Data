How do I write a postmortem that is blameless and actually useful?
@@@ ASSISTANT
A postmortem is a timeline of facts, a list of verified causes, and a set of owned fixes. It is not a verdict on any person.

Structure:

1. **Summary (3 lines).** What happened, when, for how long, and the user impact.
2. **Timeline.** Timestamped facts only: deploys, alerts, actions taken, workarounds. No interpretation in this section.
3. **Root causes.** Verified, with evidence. "The migration added a non-null column without a default, and the new code path wrote before the migration finished."
4. **What worked.** Detection, rollback, communication. Credit the system and the responders.
5. **What did not work.** Where the system allowed the error: missing test, no load test, alert that fired late.
6. **Action items.** Each item: owner, deadline, and a measurable done criterion. "Add a migration smoke test to CI. Owner: Dana. Due: Dec 5."
7. **Follow-ups.** Open questions and monitoring to add.

Rules:
- "Human error" is never a root cause. If a person could make the mistake, the system must prevent it. Replace it with the missing guardrail.
- Blame the process, not the person: "The deploy checklist did not include a migration dry run" beats "Alex forgot to check".
- Quantify impact: users affected, duration, error rate, data loss (or confirmed none).
- Name the detection gap: how long until the first alert, and why.
- Publish internally within 48 hours. A postmortem that never ships changes nothing.
- Review action items monthly until closed. An action item without a date is a wish.

- Root cause: "The engineer made a typo in the SQL."

Answer: "The migration was applied without a dry-run in CI, and the schema change was not idempotent, so a retry produced a partial state. Fixes: idempotent migrations, a CI dry-run step, and a rollback script tested weekly."

@@@ USER
How do I write meeting agendas and follow-ups that get things done?
@@@ ASSISTANT
An agenda states decisions to make, not topics to discuss. A follow-up lists decisions, owners, and dates.

Agenda:

```
Team sync — Nov 7, 10:00, 30 min
Goal: decide the export architecture before Friday.

1. (5 min) Context: current export fails for >10k rows. (Priya)
2. (10 min) Options: sync CSV (simple, slow), async job (scalable, complex).
3. (10 min) Decision: pick one. Criteria: ship by Nov 21, support 100k rows.
4. (5 min) Owners and dates for the chosen path.

Pre-read: 1 page on the failure, link to the trace.
```

Follow-up:

```
Decisions made
- Async job export. Sync path stays for <1k rows.
- Owner: Daniel. Ship by Nov 21.
- Progress update every Tuesday until shipped.

Actions
- [ ] Daniel: add job table + worker by Nov 10.
- [ ] Priya: load test to 100k rows by Nov 14.
- [ ] Maya: update billing docs by Nov 18.

Open questions
- Who owns the DLQ alert? (decide next sync)
```

Rules:
1. **Decisions, not topics.** "Pick the export architecture" beats "Discuss exports".
2. **Timebox each item.** A total under 30 minutes forces focus.
3. **Name the owner per item** in the agenda itself.
4. **Pre-read, not in-meeting reading.** One page maximum; link it.
5. **Follow-up within 24 hours.** Decisions, owners, dates. If it is not written, it did not happen.
6. **Action items are verbs with dates.** "Daniel: add job table by Nov 10" beats "Daniel to look at jobs".
7. **Close with open questions** explicitly, so they are not lost.
8. **Cancel if there is no decision.** A sync with no decision is an email. Return the time.
@@@ END

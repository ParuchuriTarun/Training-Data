@@@ USER
We ship daily. Now a different issue: our WebSocket server hit 50k connections and started dropping messages. How do we scale it?
@@@ ASSISTANT
50k connections need backpressure, a fan-out design, and load testing — not just more memory.

1. **Backpressure**: never block the event loop on a slow client. Buffer per connection with a cap, and disconnect clients that exceed it.

```ts
ws.on("message", (data) => {
  const payload = JSON.stringify(data);
  for (const client of roomClients) {
    if (client.bufferedAmount > 1_000_000) { client.terminate(); continue; }
    client.send(payload);
  }
});
```

2. **Fan-out**: one server cannot hold 50k connections. Use a pub/sub layer (Redis) so any server can publish to any room:

```ts
await redis.publish(`room:${roomId}`, JSON.stringify(msg));
// each server subscribes and forwards to its local clients in that room
```

3. **Connection admission**: cap connections per server (e.g., 10k), reject with `1013` (try again later) beyond the cap, and scale horizontally.
4. **Heartbeat + timeout**: ping every 30 s; close dead connections. Dead sockets are the usual cause of "memory grows forever".

@@@ USER
Largest room is 5,000 users. A single message fans out to 5,000 sockets. That is the hot spot. How do we handle it?
@@@ ASSISTANT
5,000 sockets per message is the design problem. Serialize once, send in batches, and do not block the event loop.

```ts
const payload = JSON.stringify(msg);
const clients = [...roomClients]; // snapshot
let i = 0;
function sendBatch() {
  const end = Math.min(i + 500, clients.length);
  for (; i < end; i++) {
    const c = clients[i];
    if (c.readyState === 1 && c.bufferedAmount < 1_000_000) c.send(payload);
    else if (c.bufferedAmount >= 1_000_000) c.terminate();
  }
  if (i < clients.length) setImmediate(sendBatch); // yield the loop
}
sendBatch();
```

Rules:
- **Serialize once** per message, not per recipient. This is usually 80% of the win.
- **Batch in chunks** (`setImmediate` every 500) so a 5,000-fan-out does not block the event loop for hundreds of milliseconds.
- **Buffer cap + terminate** slow clients. One slow client must not consume memory for 5,000.
- For very large rooms, consider a tiered fan-out: one server owns the room and publishes to other servers via Redis, which then fan out locally. That spreads the 5,000 sends across servers.
- Measure with per-send latency, not just throughput. p99 send latency is the user-visible number.

Retest: 5,000-member room, one message, assert p99 send latency under 100 ms and the event loop stays responsive (a concurrent request is served during the fan-out).

- Redis pub/sub for fan-out, 2–3 servers at 25k.

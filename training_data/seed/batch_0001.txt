@@@ USER
Why does this print B before A? I expected the timeout to run first.

```js
setTimeout(() => console.log("A"), 0);
Promise.resolve().then(() => console.log("B"));
console.log("C");
```
@@@ ASSISTANT
It prints `C`, `B`, `A`. The timeout callback is a macrotask; the promise callback is a microtask. After the current script finishes, the engine drains the entire microtask queue before it runs the next macrotask, even when the timer delay is 0.

Step by step:

1. `setTimeout` registers a macrotask and returns immediately.
2. `Promise.resolve().then(...)` queues a microtask.
3. `console.log("C")` runs as part of the current synchronous script.
4. The call stack is empty, so the engine drains microtasks: `B`.
5. Only then does the event loop pick the next macrotask: `A`.

`queueMicrotask(fn)` and `await` schedule the same kind of work as `.then`, so this ordering holds inside async functions too:

```js
async function run() {
  console.log("1");
  await null;          // continuation becomes a microtask
  console.log("3");
}
run();
console.log("2");      // 1, 2, 3
```

In Node.js there is one extra queue: `process.nextTick` callbacks run before promise microtasks, so `process.nextTick(() => console.log("N"))` beats a `.then` queued in the same tick. Browser code does not have that distinction.

Practical consequences:

- Starving the microtask queue blocks rendering. A recursive `Promise.resolve().then(loop)` never yields to the browser; use `setTimeout(loop, 0)` or `requestAnimationFrame` to give the renderer a turn.
- Do not rely on `setTimeout(..., 0)` for ordering; the minimum delay is clamped (often to 4 ms after nested timers) and other macrotasks may already be queued.
- If you need work after the DOM has been painted, use `requestAnimationFrame` followed by `setTimeout(..., 0)` or `requestIdleCallback` where available.

You can verify the order in any browser console or with `node -e` using the snippet above.
@@@ END

@@@ USER
My web app needs to queue POST requests while offline and replay them in order when the connection returns. Should I use localStorage or IndexedDB? Show me a minimal implementation without a library.
@@@ ASSISTANT
Use IndexedDB. `localStorage` is synchronous, capped around 5 MB, stores only strings, and has no transactions, so two tabs can corrupt the queue. IndexedDB is asynchronous, transactional, and handles structured data.

The design:

- Store each pending request with an auto-incrementing key so replay preserves creation order.
- Give every request an idempotency key so a retry after an ambiguous network failure cannot create a duplicate on the server.
- Delete the entry only after the server acknowledges it.
- Retry with exponential backoff and stop on 4xx responses that will never succeed.

```js
const DB_NAME = "offline-queue";
const STORE = "requests";

function openDb() {
  return new Promise((resolve, reject) => {
    const req = indexedDB.open(DB_NAME, 1);
    req.onupgradeneeded = () => {
      req.result.createObjectStore(STORE, { keyPath: "id", autoIncrement: true });
    };
    req.onsuccess = () => resolve(req.result);
    req.onerror = () => reject(req.error);
  });
}

async function tx(mode, fn) {
  const db = await openDb();
  return new Promise((resolve, reject) => {
    const t = db.transaction(STORE, mode);
    const store = t.objectStore(STORE);
    let result;
    Promise.resolve(fn(store)).then((value) => { result = value; });
    t.oncomplete = () => { db.close(); resolve(result); };
    t.onerror = () => { db.close(); reject(t.error); };
    t.onabort = () => { db.close(); reject(t.error); };
  });
}

export async function enqueue(url, body) {
  const record = {
    url,
    body,
    idempotencyKey: crypto.randomUUID(),
    attempts: 0,
    createdAt: Date.now(),
  };
  await tx("readwrite", (store) => new Promise((resolve, reject) => {
    const req = store.add(record);
    req.onsuccess = () => resolve(req.result);
    req.onerror = () => reject(req.error);
  }));
}

async function pending() {
  return tx("readonly", (store) => new Promise((resolve, reject) => {
    const req = store.getAll();
    req.onsuccess = () => resolve(req.result);
    req.onerror = () => reject(req.error);
  }));
}

async function remove(id) {
  await tx("readwrite", (store) => new Promise((resolve, reject) => {
    const req = store.delete(id);
    req.onsuccess = () => resolve();
    req.onerror = () => reject(req.error);
  }));
}

let flushing = false;

export async function flush() {
  if (flushing || !navigator.onLine) return;
  flushing = true;
  try {
    for (const item of await pending()) {
      try {
        const res = await fetch(item.url, {
          method: "POST",
          headers: {
            "Content-Type": "application/json",
            "Idempotency-Key": item.idempotencyKey,
          },
          body: JSON.stringify(item.body),
        });
        if (res.ok) {
          await remove(item.id);
          continue;
        }
        if (res.status >= 400 && res.status < 500 && res.status !== 429) {
          await remove(item.id); // permanent failure: do not retry forever
          continue;
        }
        throw new Error(`HTTP ${res.status}`);
      } catch {
        // Stop the loop to preserve ordering; retry later.
        break;
      }
    }
  } finally {
    flushing = false;
  }
}

window.addEventListener("online", flush);
setInterval(flush, 30_000);
```

Server side, the idempotency key must be unique per user and stored with the response. On a duplicate key, return the original response instead of performing the write again.

Two details that matter in production:

1. Replay is sequential on purpose. Sending requests in parallel can reorder dependent writes.
2. Register a service worker only if you also need to replay while the tab is closed. The code above flushes while the page is open; a Background Sync handler covers the closed-tab case.

Test it in DevTools: set Network to Offline, submit the form, confirm one row in IndexedDB under Application, go online, and verify the request fires once and the row disappears.
@@@ END

@@@ USER
We run a multi-tenant SaaS on Postgres and every table has a tenant_id. How do I guarantee tenant A can never read tenant B's rows, even if an endpoint forgets a WHERE clause?
@@@ ASSISTANT
Use Postgres row-level security (RLS) with a per-request tenant setting, and connect as a role that does not have `BYPASSRLS`. The database then enforces isolation regardless of what the query forgets.

Schema:

```sql
CREATE TABLE invoices (
  id          bigserial PRIMARY KEY,
  tenant_id   uuid NOT NULL,
  amount_cents integer NOT NULL,
  created_at  timestamptz NOT NULL DEFAULT now()
);

CREATE INDEX invoices_tenant_created_idx
  ON invoices (tenant_id, created_at DESC);

ALTER TABLE invoices ENABLE ROW LEVEL SECURITY;
ALTER TABLE invoices FORCE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation ON invoices
  USING (tenant_id = current_setting('app.tenant_id', true)::uuid)
  WITH CHECK (tenant_id = current_setting('app.tenant_id', true)::uuid);
```

`FORCE ROW LEVEL SECURITY` matters: without it, the table owner bypasses policies.

The application role must not own the tables and must not have `BYPASSRLS`:

```sql
CREATE ROLE app_user LOGIN PASSWORD '...' NOBYPASSRLS;
GRANT SELECT, INSERT, UPDATE, DELETE ON invoices TO app_user;
GRANT USAGE ON SCHEMA public TO app_user;
```

Set the tenant inside the same transaction as the query, using a parameter, never string interpolation:

```js
async function withTenant(pool, tenantId, fn) {
  const client = await pool.connect();
  try {
    await client.query("BEGIN");
    await client.query("SELECT set_config('app.tenant_id', $1, true)", [tenantId]);
    const result = await fn(client);
    await client.query("COMMIT");
    return result;
  } catch (err) {
    await client.query("ROLLBACK");
    throw err;
  } finally {
    client.release();
  }
}

// usage
const rows = await withTenant(pool, tenantId, (client) =>
  client.query("SELECT * FROM invoices ORDER BY created_at DESC LIMIT 50")
);
```

The `true` third argument to `set_config` makes the setting local to the transaction, so pooled connections cannot leak a tenant between requests. This is the most common RLS bug: using `SET` instead of `SET LOCAL` and poisoning a connection pool.

For inserts, the `WITH CHECK` clause rejects a row whose `tenant_id` does not match, so an attacker cannot write into another tenant by supplying a different id.

Testing:

```sql
BEGIN;
SELECT set_config('app.tenant_id', '11111111-1111-1111-1111-111111111111', true);
SELECT count(*) FROM invoices;  -- only tenant A
INSERT INTO invoices (tenant_id, amount_cents)
VALUES ('22222222-2222-2222-2222-222222222222', 100);  -- must fail
ROLLBACK;
```

Operational notes:

- Run migrations and background jobs under a separate owner role; do not reuse the app role with elevated rights.
- Add `tenant_id` to every unique constraint and foreign key that is tenant-scoped.
- Test the negative case in CI: connect as `app_user`, set tenant A, and assert that a query for tenant B's known id returns zero rows.
- RLS adds a predicate to every query; the `(tenant_id, ...)` index keeps it cheap.

Make the unsafe patterns fail loudly instead of relying on review.

1. Lint boundaries. Add `no-restricted-globals` for `window`, `document`, `localStorage`, and `navigator` in files that are not explicitly client-only, and require the `"use client"` directive for components that use hooks. In a Next.js App Router codebase, a common convention is a `use client` boundary at leaf components and a lint rule that flags browser globals in `app/**/page.tsx` and `layout.tsx`.

2. Type-level separation. Keep server data fetching in `page.tsx` and pass plain serializable props to a client component. If a prop is a function, a `Date`, or a class instance, serialization fails at build time rather than producing a subtle mismatch.

3. A single client-only primitive. Provide a `<ClientOnly>` component that renders `null` on the server and its children after mount. Use it for charts, maps, editors, and anything that reads browser state. This is safer than scattering `useEffect` guards.

```tsx
"use client";
import { useEffect, useState } from "react";

export function ClientOnly({ children, fallback = null }: {
  children: React.ReactNode;
  fallback?: React.ReactNode;
}) {
  const [mounted, setMounted] = useState(false);
  useEffect(() => setMounted(true), []);
  return mounted ? <>{children}</> : <>{fallback}</>;
}
```

4. A Playwright smoke test in CI. Load the five most important routes with JavaScript enabled, fail on any console error containing "hydration", and run it against a production build (`next build && next start`). Development-only warnings hide production behavior differences.

5. A tiny server/client contract test. For pages that render dates or prices, snapshot the server HTML and assert that the first client render matches. React's `hydrateRoot` error is the signal; do not suppress it globally.

Finally, document the rule in the README: browser state is read only after mount, theme is applied by the head script, and no component reads `localStorage` during render. That is the invariant the lint rules and tests enforce.

@@@ USER
Show me how to model async data in TypeScript so impossible states cannot happen. I keep ending up with isLoading and error as separate booleans that contradict each other.
@@@ ASSISTANT
Use one discriminated union where each state carries exactly the data it needs. The compiler then rejects access to `data` when the state is `loading` or `error`.

```ts
type AsyncState<T> =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "success"; data: T }
  | { status: "error"; error: Error };

function isSuccess<T>(s: AsyncState<T>): s is { status: "success"; data: T } {
  return s.status === "success";
}
```

A reducer makes the transitions explicit:

```ts
type Action<T> =
  | { type: "fetch" }
  | { type: "resolve"; data: T }
  | { type: "reject"; error: Error };

function reducer<T>(state: AsyncState<T>, action: Action<T>): AsyncState<T> {
  switch (action.type) {
    case "fetch":
      return { status: "loading" };
    case "resolve":
      return { status: "success", data: action.data };
    case "reject":
      return { status: "error", error: action.error };
  }
}
```

Consume it with an exhaustive switch. If a new status is added later, the `never` assignment makes the build fail until every branch is handled:

```tsx
function View({ state }: { state: AsyncState<User[]> }) {
  switch (state.status) {
    case "idle":
      return <p>Press search to load users.</p>;
    case "loading":
      return <Spinner />;
    case "error":
      return <p role="alert">Could not load users: {state.error.message}</p>;
    case "success":
      return <ul>{state.data.map((u) => <li key={u.id}>{u.name}</li>)}</ul>;
    default: {
      const exhaustive: never = state;
      return exhaustive;
    }
  }
}
```

Why this is better than `{ data, isLoading, error }`:

- `data` cannot be `undefined` while the UI claims success.
- An error and a success payload cannot coexist.
- Refreshing does not force you to clear previous data unless you add a `refreshing` state deliberately, for example `{ status: "success"; data: T; refreshing: true }`.
- `switch` gives autocomplete and exhaustiveness checking.

Two practical additions:

1. Wrap the request in an async function that dispatches `resolve` or `reject`, and guard against out-of-order responses with an `AbortController`.
2. If you use TanStack Query, you already get this model; keep the same union at component boundaries rather than destructuring `isLoading`, `isError`, and `data` into separate booleans.

A quick test case proves the invariant: construct each variant and assert that rendering never reads `data` unless `status === "success"`. TypeScript enforces it at compile time, and the test documents the contract.

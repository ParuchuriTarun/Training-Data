@@@ USER
How do I write UX copy for empty states and error messages?
@@@ ASSISTANT
Two rules: name the user's next step, and say what the system did. Every message should let a first-time user act without help.

Empty state pattern:

- Headline (what this is): "No projects yet"
- One line (why it matters): "Create a project to assign tasks and track progress."
- One primary action: [Create project]
- Optional secondary link: "View a sample project"

Error pattern:

- What happened: "We couldn't save your changes."
- What it means: "Your draft is still on this device."
- Next step: "Check your connection and try again."

Rules:
1. One action per screen. Two buttons compete; the user does neither.
2. Verbs name outcomes: "Create project", "Delete 12 messages", "Download invoice (PDF)". Never "Click here", "OK", or "Submit".
3. Errors blame the system, not the user: "We couldn't load your orders" beats "You have no orders" when the request failed.
4. Say what was saved. "Your draft is saved. The payment did not go through." Prevents duplicate work.
5. Confirm destructive actions by repeating the object: dialog "Delete project?" with confirm "Delete project", not "Yes".
6. Field errors inline, not in a toast that disappears.
7. Keep tone calm for money and data-loss errors. No "Oops!" on a payment failure.
8. Every error needs a next step: "Try again", "Sign in", "Choose a smaller file".

Exercise: rewrite these.

1. "No data found."
2. "Error 400"
3. "Submit"

Answers:

1. "No projects yet. Create your first project to start tracking work." [Create project]
2. "We couldn't read that request. Check the fields and try again."
3. "Send message" or "Publish post" — the verb matches the action.
@@@ END

@@@ USER
How do I write console errors and API error messages for developers?
@@@ ASSISTANT
Developers need three things: a stable code, a human sentence, and the request id.

```json
{
  "error": {
    "code": "validation_error",
    "message": "The email field is invalid.",
    "details": { "field": "email", "reason": "invalid_format" },
    "requestId": "req_9fK2a"
  }
}
```

Rules:
1. `code` is the machine contract. Clients branch on it. Never change a published code's meaning.
2. `message` is for humans. It can improve without breaking clients.
3. `details` carries field and reason so a form can highlight the exact input.
4. `requestId` matches the `X-Request-Id` header and the server log line. Without it, every bug report becomes a guess.
5. Status codes: 400 validation, 401 unauthenticated, 403 forbidden, 404 not found, 409 conflict, 413 too large, 422 semantic validation, 429 rate limited, 5xx internal.
6. Never expose SQL, stack traces, or internal URLs in a message. Log them server-side with the request id.
7. One error shape for the whole API. Ad-hoc shapes per endpoint double the client code.
8. Log every 5xx with user id, route, and duration. A 500 with no log line is unfixable.

Exercise: fix this response.

- `500 { "error": "TypeError: Cannot read properties of undefined (reading 'email') at users.ts:42" }`

Answer: `500 { "error": { "code": "internal_error", "message": "Something went wrong.", "requestId": "req_9fK2a" } }` with the stack logged server-side under that request id.
@@@ END

@@@ USER
How do I write a postmortem that is blameless and useful?
@@@ ASSISTANT
Facts first, causes with evidence, fixes with owners and dates. Never a verdict on a person.

Structure:

1. **Summary (3 lines).** What happened, when, how long, user impact.
2. **Timeline.** Timestamped facts only: deploys, alerts, actions, workarounds.
3. **Root causes.** Verified, with evidence. "The migration added a non-null column without a default, and the new code wrote before the migration finished."
4. **What worked.** Detection, rollback, communication.
5. **What did not work.** The missing guardrail: test, load test, or late alert.
6. **Action items.** Owner + deadline + measurable done criterion.

Rules:
- "Human error" is never a root cause. If a person could make the mistake, the system must prevent it. Replace it with the missing guardrail.
- Blame the process: "The deploy checklist lacked a migration dry run" beats "Alex forgot to check".
- Quantify: users affected, duration, error rate, confirmed data loss or none.
- Publish within 48 hours. Review action items monthly until closed. An action item without a date is a wish.

Exercise: rewrite this root cause.

- "The engineer made a typo in the SQL."

Answer: "The migration ran without a CI dry run and was not idempotent, so a retry left a partial state. Fixes: idempotent migrations, a CI dry-run step, and a tested rollback script."
@@@ END

@@@ USER
How do I answer behavioral interview questions with STAR?
@@@ ASSISTANT
Situation, Task, Action, Result. The interviewer wants to see how you reason.

- **Situation (2 sentences).** Roles and the decision. "We were designing the payments API and my teammate wanted to store card tokens in our database."
- **Task (1 sentence).** What you had to decide. "I needed to pick a storage model before the processor contract was signed."
- **Action (the bulk).** What you did. "I asked for the compliance requirements from our processor, wrote a one-page comparison, and proposed a trial with the token vault."
- **Result (1–2 sentences with numbers).** "We adopted the vault; card data never touches our servers, and the audit passed without findings."

Rules:
- Stay on your actions. Never "he was wrong".
- Admit what you learned: "I should have involved security earlier."
- Under 90 seconds spoken. Details only if asked.
- No confidential details: company names, figures, unpublished features.
- End with the outcome, not the conflict.
@@@ END

@@@ USER
How do I paraphrase a source without plagiarizing it?
@@@ ASSISTANT
Paraphrasing changes structure and emphasis; plagiarism is reusing ideas or phrases without credit.

Original:

"Primary keys should be immutable and unique. A surrogate integer key is simple, but it requires an extra lookup for business queries, so many teams prefer a natural key."

Patchwriting (wrong):

- "Immutable and unique primary keys are recommended. Surrogate integer keys are simple, though they need an extra lookup for business queries, so natural keys are preferred by many teams."

Proper rewrite (your analysis):

- "In our schema we use a database-generated UUID that never changes. Business identifiers like order numbers live in a separate unique column because lookups by order number are handled by an index."

Rules:
1. Read, close, write. Close the source, then write from memory.
2. Change structure, not synonyms. Swapping "recommended" for "suggested" is not paraphrasing.
3. Cite anyway. Ideas need credit even in your own words.
4. Add your own content: a decision, a number, a tradeoff.
5. Short quotes are fine with quotation marks and a citation.
6. Common knowledge does not need citation; specific empirical claims do.
@@@ END

@@@ USER
How do I write UX copy for empty states and error messages?
@@@ ASSISTANT
Two rules: name the user's next step, and say what the system did.

Empty state:

- "No projects yet. Create your first project to start tracking work." [Create project]
- "No notifications. You're all caught up."
- "Your inbox is empty. Invite a teammate to get started." [Invite teammate]

Error:

- "We couldn't save your changes. Check your internet connection and try again."
- "This email is already registered. Try signing in instead."
- "The file is larger than 25 MB. Choose a smaller file or compress it."

Rules:
1. One action per screen.
2. Verbs name outcomes: "Create project", "Delete 12 messages". Never "Click here" or "OK".
3. Errors blame the system, not the user.
4. Say what was saved: "Your draft is saved. The payment did not go through."
5. Confirm destructive actions by repeating the object.
6. Field errors inline, not in a disappearing toast.
7. Calm tone for money and data-loss errors.
8. Every error needs a next step.

Exercise: rewrite "No data found.", "Error 400", "Submit".

Answers: "No projects yet. Create your first project to start tracking work.", "We couldn't read that request. Check the fields and try again.", "Send message" or "Publish post".
@@@ END

@@@ USER
How do I write console errors and API error messages for developers?
@@@ ASSISTANT
A stable code, a human sentence, and the request id.

```json
{
  "error": {
    "code": "validation_error",
    "message": "The email field is invalid.",
    "details": { "field": "email", "reason": "invalid_format" },
    "requestId": "req_9fK2a"
  }
}
```

Rules:
1. `code` is the machine contract; never change a published code's meaning.
2. `message` can improve without breaking clients.
3. `details` carries field + reason so a form can highlight the exact input.
4. `requestId` matches the `X-Request-Id` header and the server log.
5. Status codes: 400 validation, 401 unauthenticated, 403 forbidden, 404 not found, 409 conflict, 422 semantic, 429 rate limited, 5xx internal.
6. Never expose SQL, stack traces, or internal URLs. Log them server-side.
7. One error shape for the whole API.
8. Log every 5xx with user id, route, and duration.

Exercise: fix `500 { "error": "TypeError: Cannot read properties of undefined (reading 'email') at users.ts:42" }`. Answer: `500 { "error": { "code": "internal_error", "message": "Something went wrong.", "requestId": "req_9fK2a" } }` with the stack logged server-side.
@@@ END

How do I write a postmortem that is blameless and useful?
@@@ ASSISTANT
Facts first, causes with evidence, fixes with owners and dates.

Structure:

1. Summary (3 lines): what happened, when, how long, impact.
2. Timeline: timestamped facts only.
3. Root causes: verified, with evidence.
4. What worked: detection, rollback, communication.
5. What did not work: the missing guardrail.
6. Action items: owner + deadline + measurable done criterion.

Rules:
- "Human error" is never a root cause. Replace it with the missing guardrail.
- Blame the process, not the person.
- Quantify: users affected, duration, error rate, confirmed data loss or none.
- Publish within 48 hours. Review action items monthly. An action item without a date is a wish.

Exercise: rewrite "The engineer made a typo." Answer: "The migration ran without a CI dry run and was not idempotent, so a retry left a partial state. Fixes: idempotent migrations, a CI dry-run step, and a tested rollback script."
@@@ END

How do I answer behavioral interview questions with STAR?
@@@ ASSISTANT
Situation, Task, Action, Result, under 90 seconds, on your actions.

- **Situation (2 sentences).** "We were designing the payments API and my teammate wanted to store card tokens in our database."
- **Task (1 sentence).** "I needed to pick a storage model before the processor contract was signed."
- **Action (the bulk).** "I asked for the compliance requirements, wrote a one-page comparison, and proposed a trial with the token vault."
- **Result (1–2 sentences with numbers).** "We adopted the vault; card data never touches our servers, and the audit passed without findings."

Rules:
- Stay on your actions.
- Admit what you learned.
- No confidential details.
- End with the outcome.
@@@ END

@@@ USER
How do I paraphrase a source without plagiarizing it?
@@@ ASSISTANT
Change structure and emphasis; cite ideas even in your own words.

Original: "Primary keys should be immutable and unique. A surrogate integer key is simple, but it requires an extra lookup for business queries, so many teams prefer a natural key."

Patchwriting (wrong): "Immutable and unique primary keys are recommended. Surrogate integer keys are simple, though they need an extra lookup..."

Proper rewrite: "In our schema we use a database-generated UUID that never changes. Business identifiers like order numbers live in a separate unique column because lookups by order number are handled by an index."

Rules:
1. Read, close, write.
2. Change structure, not synonyms.
3. Cite anyway.
4. Add your own content: a decision, a number, a tradeoff.
5. Short quotes need quotation marks and a citation.
6. Common knowledge needs no citation; specific claims do.
@@@ END
